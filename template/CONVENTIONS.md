# Go Conventions

m0t0k1ch1-go 配下の Go リポジトリに共通するコーディング規約。コードを書く・変更するときは、以下に従う。

## 指針

指針同士が衝突したときは、番号の小さい指針を優先する。

### 1. Stay Consistent

同じ意味のものは同じ形で書く。新しい型・関数・エラー・コメントを書く前に、同じリポジトリか兄弟リポジトリの既存実装を探し、その形（命名、レシーバ名、メソッドの並び、エラー文言、godoc の一文目）を写す。より良い書き方を思いついても既存に揃え、揃えられない理由があるときだけ PR 説明に書く。既存側を直す統一作業は人間が別途行う。

### 2. Fail Fast

異常系は処理の入口で全て排除し、その先のロジックは正常系だけを前提に書く。入口とは外から値が入ってくる境界（引数の受け取り、デコード、設定や入力の読み込み）であり、検証はそこに集約し、通過した値は以降どこでも正しいものとして扱う。想定外の入力・状態・型は、補正や既定値で吸収せず、原因が分かるエラーで即座に返す。関数は前提条件の確認から始め、満たさなければその場で return する。

### 3. Keep Minimal

求められた変更に必要な最小限だけを書く。新しい依存、公開 API、オプション、ヘルパー、防御的な nil チェック、ログ、コメントは、テストか要求が必要としない限り足さない。標準ライブラリで書けるものは標準ライブラリで書く。迷ったら「これを消してもテストが通るか」を基準にし、通るなら消す。

## 前提

- 変更後は `make lint` と `make test` を必ず通す。
- テストコード、`staticcheck.conf`、`Makefile`、`conventions.mk`、CI 設定を変更・削除・スキップして通してはならない。これらは人間が管理する。

## 規則

指針ごとの具体的な規則。今後追記する。

### Stay Consistent

- Go 1.27 を前提に書く。ビルドが通ればよいという意味ではなく、Go 1.27 の時点で推奨されている API と書き方を使い、非推奨になった API や、新しい標準パッケージに置き換えられた古いパッケージは使わない。
  - 例：JSON の処理には `encoding/json` を使わず、`encoding/json/v2` と `encoding/json/jsontext` を使う。
- ファイル名は小文字にし、そのファイルで定義する型または機能の名前を付ける。パッケージ名と同じ名前のファイルは必須ではないが、置く場合はそのパッケージの入口にする。テストは、対象のファイル名に `_test.go` を付けたファイルに書き、対象のファイルと 1 対 1 で対応させる。
- import 文は、標準ライブラリのパッケージ、サードパーティのパッケージ、同じモジュール内のパッケージの 3 つのグループに分け、この順に並べる。グループの間は空行で区切り、グループの中には空行を入れない。
- 値を変更しないメソッドは値レシーバ、変更するメソッドはポインタレシーバにする。型が満たすインターフェースは、ファイル先頭で `var _ fmt.Stringer = T{}` のように宣言する。
- エラーメッセージは小文字で始め、末尾にピリオドを付けない。文言は以下の既存の定型に揃え、新しい定型を作らない。`: ` 以降の補足は、付けるものがなければ省く。
  - `invalid <対象>: <理由>`
  - `unsupported <対象>: <渡された値または型>`
  - `failed to <動作>: %w`
- 変数のスコープはできるだけ狭くする。一部でしか使わない変数は、裸のブロック `{ … }` で囲んで外に漏らさない。
- `interface{}` ではなく `any` を使う。
